## Executive Summary

This investigation successfully reproduced and documented the **actual DeepSeek web application backend protocol** through a combination of:

1. **HAR analysis** — Firefox network capture of official web UI
2. **Live API testing** — Python client against production endpoint
3. **Systematic experimentation** — Header replay matrix, model_type, search, action, error conditions
4. **Architecture redesign** — Session state model, dynamic header abstraction

**Key Finding:** The DeepSeek web protocol is **reproducible for text-only streaming**, but **automated authentication is blocked by per-request Proof-of-Work (PoW) generated by browser WebAssembly (`DeepSeekHashV1`)** and a fingerprint header (`x-hif-leim`).

4. `Cookie` — Optional if auth+PoW+hif valid

## 4. Dynamic Header Generation Flow (NEW - from did.txt)

### Complete Dynamic Header Generation Sequence

```
1. GET https://hif-leim.deepseek.com/query
   → Returns: {"value": "token1.token2"} (x-hif-leim)
   → Header: x-hif-ttl: 600 (10 min TTL)

2. POST https://chat.deepseek.com/api/v0/chat/create_pow_challenge
   Body: {"target_path": "/api/v0/chat/completion"}
   → Returns: challenge object (see below)
   → TTL: expire_after: 300000ms (5 min)

3. Browser WASM (sha3_wasm_bg.7b9ca65ddd.wasm) computes PoW
   Input: challenge + salt + difficulty
   Output: x-ds-pow-response (Base64 JSON)

4. POST /api/v0/chat/completion with:
   - Authorization: Bearer <token>
   - Cookie: ds_session_id, smidV2
   - x-ds-pow-response: <from step 3>
   - x-hif-leim: <from step 1>
```

### PoW Challenge Endpoint
**Endpoint:** `POST https://chat.deepseek.com/api/v0/chat/create_pow_challenge`
**Request:** `{"target_path": "/api/v0/chat/completion"}`

**Response (from did.txt):**
```json
{
  "algorithm": "DeepSeekHashV1",
  "challenge": "780f82ae19064aaff9881fa8b4251816b702b4ecc80bc2af73ec965199a969ee",
  "salt": "d171f1aec3da3ac48f57",
  "signature": "3b5d8f80f3592e5a6b4b682eb13186798afa7790524c1133c17e4b18aae5378b",
  "difficulty": 144000,
  "expire_after": 300000,
  "target_path": "/api/v0/chat/completion"
}
```
- `difficulty`: 144000 (target iterations)
- `expire_after`: 300000ms (5 minutes)
- `expire_at`: Unix timestamp ms

## 5. Protocol Specification Summary

### Endpoint
```
POST https://chat.deepseek.com/api/v0/chat/completion
Content-Type: application/json
Response: text/event-stream (SSE)
```

### Valid model_type Values
| Value | Status |
|-------|--------|
| `expert` | ✅ Accepted |
| `default` | ✅ Accepted |
| `vision` | ✅ Accepted (from error message) |
| `chat` | ❌ Rejected (422) |
| `reasoning` | ❌ Rejected (422) |

### Valid action Values
| Value | Status |
|-------|--------|
| `default` | ✅ Accepted |
| `retry` | ✅ Accepted |
| `continue` | ❌ Rejected (422) |
| `regenerate` | ❌ Rejected (422) |
| `edit` | ❌ Rejected (422) |
| `stop` | ❌ Rejected (422) |

### SSE Event Types
| Event | Description |
|-------|-------------|
| `ready` | Stream start; contains `request_message_id`, `response_message_id`, `model_type` |
| `update_session` | Session timestamp (`updated_at`) |
| `data` (unnamed) | JSON Patch ops: `response/fragments/-1/content` (APPEND), `response/status` (SET), `response/fragments` (APPEND), `response` (BATCH) |
| `title` | Auto-generated conversation title |
| `close` | Stream end (`click_behavior`, `auto_resume`) |

### Fragment Types
| Type | Description |
|------|-------------|
| `THINK` | Model's internal reasoning (streamed) |
| `RESPONSE` | Final user-visible answer |

## 5. Tool Calling — Final Determination

**Classification: `TEXT_ONLY` / `NOT_FOUND`**

**Evidence:**
- Zero occurrences of `tool_calls`, `function_calls`, `tools`, `actions`, `plugins`, `mcp`, `command` in:
  - Request payloads
  - SSE response events
  - HAR network traffic (all 7 entries analyzed)
- Only fragment types: `THINK` and `RESPONSE`
- Search is a boolean flag, not a tool protocol
- File upload (`ref_file_ids`) field exists but upload flow unobserved

**Implication:** DeepSeek web is **text-only streaming**. An OpenAI-compatible proxy would need:
- Text-based tool calling shim (prompt injection + JSON parsing)
- External executor for tool calls
- This is architecturally different from native OpenAI function calling

## 9. Architecture Recommendation

### Recommended: Browser-Assisted Proxy (Architecture B)

```text
┌─────────────────────────────────────────────────────────────┐
│                    DeepFree Proxy                            │
├─────────────────────────────────────────────────────────────┤
│  OpenAI API Layer                                           │
│  ├── POST /v1/chat/completions                              │
│  ├── Streaming translation (SSE → OpenAI chunks)            │
│  └── Tool calling shim (text-based)                         │
├─────────────────────────────────────────────────────────────┤
│  DeepSeek Adapter                                            │
│  ├── Session management (AuthState + ChatSession)           │
│  ├── DynamicHeaderProvider (pluggable)                      │
│  │   └── BrowserDynamicHeaderProvider (Playwright)          │
│  └── Error handling / retry logic                           │
├─────────────────────────────────────────────────────────────┤
│  Playwright Browser (headless)                               │
│  ├── Google OAuth login                                     │
│  ├── Session persistence (cookies + localStorage)           │
│  ├── PoW generation (executes DeepSeekHashV1 WASM)          │
│  └── x-hif-leim generation                                  │
└─────────────────────────────────────────────────────────────┘
```

**Why not pure Python (Architecture A)?** PoW (`DeepSeekHashV1`) is WebAssembly — reversing it is fragile and ToS-risky. Browser automation is the legitimate path.

**Why not pure browser (Architecture C)?** Too slow for production proxy; Python HTTP client is 100x faster for completion requests once headers are generated.
